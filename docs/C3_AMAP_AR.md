# 特会开 C3 实景 / 高德 AR 接入

基于用户提供的 `c3-amap-ar-adaptation-20261015` 原型包。仅接入停车测试能力，不改变导航、控制、C3 参数或启动配置。

## 结构与兼容性

设置 →「C3 实景 · 高德 AR（停车测试）」配置 C3 `/frames` 地址和本次 48 位测试令牌，手动开始/停止。
实际网络接收、YUV 转换、共享内存及状态均在特会开 `C3ArCameraService`。
高德原版按固定包 `com.autonavi.amapauto.gdarcameraservicedemo` 查找接口，因此 `arcompat` 是必要的单独 APK，仅转发 Binder，没有网络、令牌、画面或后台常驻逻辑。不能仅将 Java 类名放入主 APK 来冒充这个安装包身份。
两个 APK 必须同签名：特会开服务要求 signature 权限；兼容入口只允许安装的高德包 UID 调用，服务只接受兼容入口 UID。没有增加相机权限或 root / Stellar 依赖。现有高德界面嵌入仍按原机制运行。

原型只验证高德 6.1.5.600089，普通版或其他版本可能没有此接口。不替换、修改或自动安装高德。
原型桥接 APK 使用另一个测试签名，不能直接覆盖为本兼容入口；如设备已安装旧桥接，应先确认旧测试已停止，再经用户授权处理签名冲突。不得卸载高德或清除特会开数据来解决冲突。

## 构建及使用

`gradlew.bat testDebugUnitTest assembleTenengkai :arcompat:assembleDebug assembleDebug --no-configuration-cache`

交付主 APK 为 `app/build/outputs/apk/tenengkai/app-tenengkai.apk`；配套入口 `arcompat/build/outputs/apk/debug/arcompat-debug.apk`。
不使用原型测试签名替换现有特会开签名。未来生产签名须配套签两个 APK。

C3 端沿用原包现有 `/health`、带 Bearer 鉴权的 `/frames` 长度分帧服务，默认端口 8082。本次没有复制服务器、部署依赖、自动启动远端服务或开启摄像头。须按原包说明独立准备并确认停车条件与参数恢复。
设置页输入服务地址及其当前测试令牌，开始后回到高德车机进入 AR 校准页。检查「网络帧」及「已交给高德」均增长，后者才是共享帧写入证据；这仍不证明 AR 校准准确或道路可用。
停止按钮或通知中的停止动作立即断开网络、释放共享区。后台不自动恢复；重启 App 后必须重新手动开始测试。C3 服务的 offroad 检查仍保留，HTTP401/409不重试；普通网络故障最多4次重连（1/2/4/8秒），不延长本次20分钟期限。

## 与原型的必要差异及限制

- 复用原 Binder 事务、Parcel字段顺序、YV12/NV21 和20字节共享区头/首字节握手。
- 参数只接受已接入的格式、偶数分辨率及有界 JPEG；拒绝跳转、非局域网目标和异常图片尺寸。
- 缩放保持宽高比，使用黑边补齐而非横向拉伸；原标定不可直接沿用，内参/安装位置、黑边影响仍需验证。
- 重用目标 Bitmap、像素/YUV数组；源 Bitmap 使用后回收。只有高德释放共享标志才转换/写下一帧，不保留无限帧队列。
- 回调死亡/关闭/停止清理资源；远端回调时不持有图像锁，防止高德回查状态造成死锁。
- 原 TesNav 不声明 AR 服务、权限、页面或依赖；Android8.0 的特会开仍保留原功能，AR入口要求8.1。
- 未验证新双APK链路的实机消费、长期运行、C3负载、行驶、端到端延迟或AR箭头准确性。不能把原型的出图证据当作本次版本的实机验收。
